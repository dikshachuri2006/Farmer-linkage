# Farmer Market Linkage Database Schema Specification

**Status:** proposed for review; not DDL.  
**Scope:** PostgreSQL schema for the existing FastAPI/Pydantic v2 contract.  
**Sources:** API schemas, routes, repository interfaces, tests, and `ANKITA_DATABASE_PROPOSAL.md` in this project.  
**Safety:** this document does not create tables, run migrations, connect to PostgreSQL, or change application code.

### Evidence labels used in this specification

- **Verified by current code/tests** means directly present in schemas/routes/repository interfaces or asserted by tests. The production repository implementations remain stubs; a test-double behavior is not proof of PostgreSQL persistence behavior.
- **Recommended implementation invariant** is a persistence safeguard that preserves the observed API contract. It is a recommendation for future implementation, not behavior already implemented.
- **Unresolved product/data decision** is not established by repository evidence; do not encode it as a restrictive database constraint until decided.

The column definitions below are the **recommended schema mapping**, not existing tables. Primary keys, foreign keys, unique keys, indexes, defaults, and checks below are recommended schema structure unless a bullet explicitly labels them verified. They are not claims that current persistence already enforces them.

## 1. Design decisions and identity strategy

### IDs exposed by the current API

**Recommended implementation invariant:** use `users.id` as the identity for authenticated people and in person-reference FKs. Thus `farmer_lots.farmer_id`, `buyer_offers.buyer_id`, `selling_requests.farmer_id`/`buyer_id`, and transaction participant IDs reference `users.id`. `farmer_profiles.user_id` and `buyer_profiles.user_id` are unique one-to-one references to the same user. `buyer_profiles.id` (like `farmer_profiles.id`) is an internal profile-row identifier; it is not substituted for a JWT subject or API `farmer_id`/`buyer_id`.

**Verified by current code/tests:** JWT subjects and route authorization IDs are user IDs; lot and selling-request route tests pass authenticated user IDs as `farmer_id`/`buyer_id`. The proposal points lot and trade actor FKs to profile row IDs. The `SellingRequestCreate.buyer_id` contract is resolved as the buyer's `users.id`, matching route/test behavior. The field remains an integer and retains its name and validation.

Use integer `BIGINT GENERATED BY DEFAULT AS IDENTITY` primary keys for all entities, with `BIGINT` matching foreign keys. Public human-readable references (`request_code`, `transaction_id`, `ticket_number`) are separate unique columns. No UUID requirement is evidenced by the project.

### Type conventions

- Use `TIMESTAMPTZ` for timestamps and `DATE` for business dates.
- Use `NUMERIC`, not floating point, for persisted price, quantity, and amount values. Proposed precision is noted per field; validate aggregate ranges before implementation.
- Use PostgreSQL named enums for API enums, or checked `VARCHAR` if future enum evolution needs to avoid enum DDL friction. Persist exact uppercase API values. This document describes the values as enum domains; implementation must choose one consistent representation.
- Text lengths follow Pydantic bounds where defined. A field without a schema limit should not gain an arbitrary tight limit in the database.
- `created_at` defaults to `CURRENT_TIMESTAMP`. `updated_at` is non-null and updated on writes by the repository or trigger; defaults alone do not maintain it.

## 2. Table specifications

The column lists below show `name TYPE [NULL/NOT NULL] [DEFAULT]`. “No default” means callers/repositories must supply a value. PK, FK, unique, index, and check constraints follow each table. Check constraints listed as derived should be kept aligned with Pydantic validation. The final schema review should name constraints deterministically.

### 2.6 `market_prices`

| Column | Definition |
|---|---|
| `id` | `BIGINT NOT NULL GENERATED BY DEFAULT AS IDENTITY` |
| `crop_id` | `BIGINT NOT NULL` |
| `market_id` | `BIGINT NOT NULL` |
| `price_date` | `DATE NOT NULL` |
| `min_price` | `NUMERIC(12,2) NOT NULL` |
| `max_price` | `NUMERIC(12,2) NOT NULL` |
| `modal_price` | `NUMERIC(12,2) NOT NULL` |
| `arrival_quantity` | `NUMERIC(14,3) NULL` |
| `price_unit` | `VARCHAR(30) NOT NULL DEFAULT 'INR/Quintal'` |
| `arrival_unit` | `VARCHAR(30) NULL` |
| `source` | `VARCHAR(150) NOT NULL DEFAULT 'Agmarknet'` |

- PK: `id`. FKs: `crop_id → crops.id`, `market_id → markets.id`.
- **Verified by current code/tests:** price fields and arrival quantity are nonnegative in `PriceRecordResponse`; `validate_price_bounds` rejects `max_price < min_price`.
- **Recommended implementation invariant:** retain `max_price >= min_price` and arrival quantity null or `>= 0`.
- **Unresolved product/data decision:** whether modal price must be between min and max. Current schema validator does not enforce this and synthetic fixtures do not establish a dataset rule; do not add `min_price <= modal_price <= max_price` until confirmed.
- Index: `(crop_id,market_id,price_date DESC)` as proposal. Add `(crop_id,price_date DESC)` only if actual query plans show it is useful; latest-price requests can omit market ID.
- **Unresolved product/data decision:** deduplication options are (a) unique `(source,crop_id,market_id,price_date)` for one record per source/day/market/crop; (b) include source dataset's stable record ID; (c) allow multiple observations and deduplicate in an import staging process. Current code does not define this. Do not impose a unique daily key until dataset grain and source update semantics are confirmed.

### 2.8 `buyer_offers`

**Verified by current code/tests:** buyer offers are independent of selling requests. Offer create/list/withdraw routes reference a lot, and no current route/repository interface links an offer to a selling request. Do not add an offer-to-request FK without a new contract. Smaller-than-lot quantities are accepted; residual inventory behavior is unresolved.

| Column | Definition |
|---|---|
| `id` | `BIGINT NOT NULL GENERATED BY DEFAULT AS IDENTITY` |
| `buyer_id` | `BIGINT NOT NULL` |
| `lot_id` | `BIGINT NOT NULL` |
| `offered_price_per_unit` | `NUMERIC(12,2) NOT NULL` |
| `price_unit` | `VARCHAR(30) NOT NULL DEFAULT 'INR/quintal'` |
| `quantity_requested` | `NUMERIC(14,3) NOT NULL` |
| `quantity_unit` | `VARCHAR(20) NOT NULL DEFAULT 'quintal'` |
| `pickup_included` | `BOOLEAN NOT NULL DEFAULT FALSE` |
| `delivery_location` | `VARCHAR(200) NOT NULL` |
| `status` | `offer_status NOT NULL DEFAULT 'ACTIVE'` |
| `valid_until` | `DATE NULL` |
| `terms_and_notes` | `VARCHAR(500) NULL` |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` |

- PK: `id`. FKs: `buyer_id → users.id`, `lot_id → farmer_lots.id`.
- **Verified by current code/tests:** offered price and requested quantity are positive; route rejects requested quantity greater than lot quantity.
- **Recommended implementation invariant:** database check offered price and requested quantity `> 0`; repository validates offer quantity against referenced lot under appropriate transaction protection.
- **Unresolved product/data decision:** offers smaller than lot quantity are accepted by the route. No partial inventory/residual-lot workflow is established.
- **Verified by current code/tests:** `buyer_offers` is independent of `selling_requests`. Offer create/list/withdraw routes reference a lot, and no current route/repository interface links an offer to a selling request. Do not add an offer-to-request FK without a new contract.

### 2.9 `selling_requests`

**Verified by current code/tests:** request quantity may be smaller than the referenced lot quantity; the route only rejects a request exceeding stock. This does not define partial-sale fulfillment or residual inventory handling.

| Column | Definition |
|---|---|
| `id` | `BIGINT NOT NULL GENERATED BY DEFAULT AS IDENTITY` |
| `request_code` | `VARCHAR(50) NOT NULL` |
| `farmer_id` | `BIGINT NOT NULL` |
| `buyer_id` | `BIGINT NOT NULL` |
| `lot_id` | `BIGINT NOT NULL` |
| `quantity` | `NUMERIC(14,3) NOT NULL` |
| `quantity_unit` | `VARCHAR(20) NOT NULL DEFAULT 'quintal'` |
| `proposed_price` | `NUMERIC(12,2) NOT NULL` |
| `price_unit` | `VARCHAR(30) NOT NULL DEFAULT 'INR/quintal'` |
| `estimated_gross_amount` | `NUMERIC(16,2) NOT NULL` |
| `estimated_transport_cost` | `NUMERIC(14,2) NOT NULL DEFAULT 0` |
| `estimated_other_charges` | `NUMERIC(14,2) NOT NULL DEFAULT 0` |
| `estimated_net_realization` | `NUMERIC(16,2) NOT NULL` |
| `status` | `selling_request_status NOT NULL DEFAULT 'PENDING'` |
| `rejection_reason` | `TEXT NULL` |
| `message` | `VARCHAR(500) NULL` |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` |

- PK: `id`. Unique: `request_code`. FKs: `farmer_id → users.id`, `buyer_id → users.id`, `lot_id → farmer_lots.id`.
- **Verified by current code/tests:** request quantity/proposed price are positive; estimated charges are nonnegative; route rejects request quantity above lot quantity. Mock service calculates gross as price × quantity and net as gross less charges, so net can be negative.
- **Recommended implementation invariant:** check positive quantity and proposed price and nonnegative costs. Do not constrain `estimated_net_realization >= 0`.
- **Unresolved product/data decision:** whether stored gross/net must exactly equal formulas, rounding behavior, and whether negative net realization is allowed (current API permits it). No exact arithmetic constraint is specified here.
- **Verified by current code/tests:** current route/tests pass the buyer's authenticated user ID as `buyer_id`; the field contract is `users.id`, not `buyer_profiles.id`. The ORM FK target is `users.id`.
- **Recommended implementation invariant:** the persistent repository must validate that the referenced user exists and is eligible to receive a selling request, and must test those checks. A foreign key to `users.id` enforces existence at the database level; role and verification eligibility require an explicit application rule.
- **Unresolved product/data decision:** define the exact buyer eligibility rule, including whether `users.role` must be `BUYER`, whether a `buyer_profiles` row must exist, and which `verification_status` values qualify. Do not invent or enforce a verification policy before this is decided.
- Indexes: `(farmer_id,status,created_at DESC)`, `(buyer_id,status,created_at DESC)`, `(lot_id,status)`.
- Enum: `PENDING`, `COUNTERED`, `ACCEPTED`, `REJECTED`, `CANCELLED`, `EXPIRED`, `COMPLETED`.
- API response `crop_name`, `farmer_name`, and `buyer_name` are joins; do not duplicate them. Negotiation message is accepted at creation but not returned in the current response; retaining it is recommended to avoid losing submitted API input. Whether subsequent counter notes need a history table is unresolved.

| Column | Definition |
|---|---|
| `id` | `BIGINT NOT NULL GENERATED BY DEFAULT AS IDENTITY` |
| `transaction_id` | `VARCHAR(60) NOT NULL` |
| `selling_request_id` | `BIGINT NOT NULL` |
| `farmer_id` | `BIGINT NOT NULL` |
| `buyer_id` | `BIGINT NOT NULL` |
| `crop_id` | `BIGINT NOT NULL` |
| `quantity` | `NUMERIC(14,3) NOT NULL` |
| `quantity_unit` | `VARCHAR(20) NOT NULL` |
| `agreed_price` | `NUMERIC(12,2) NOT NULL` |
| `price_unit` | `VARCHAR(30) NOT NULL` |
| `gross_amount` | `NUMERIC(16,2) NOT NULL` |
| `transport_cost` | `NUMERIC(14,2) NOT NULL DEFAULT 0` |
| `other_charges` | `NUMERIC(14,2) NOT NULL DEFAULT 0` |
| `net_amount` | `NUMERIC(16,2) NOT NULL` |
| `payment_status` | `payment_status NOT NULL DEFAULT 'PENDING'` |
| `transaction_status` | `transaction_status NOT NULL DEFAULT 'CONFIRMED'` |
| `payment_method` | `VARCHAR(50) NULL DEFAULT 'ESCROW'` |
| `notes` | `VARCHAR(500) NULL` |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP` |

- PK: `id`. Unique: `transaction_id`; **unique `selling_request_id` is mandatory**, guaranteeing at most one transaction per request, including concurrent attempts.
- FKs: `selling_request_id → selling_requests.id`, farmer/buyer IDs to `users.id`, `crop_id → crops.id`.
- **Verified by current code/tests:** creation is accepted-request-only at route level, returns initial transaction status `CONFIRMED` and payment status `PENDING`, and rejects duplicate request transactions (mock test). The transaction schema has positive trade values but does not validate amounts in Pydantic.
- **Recommended implementation invariant:** quantity and agreed price positive; costs nonnegative; `UNIQUE(selling_request_id)`; transaction farmer, buyer, crop, lot-related quantity/unit/price/charges must be derived from the linked accepted request and its lot inside the same DB transaction that revalidates `ACCEPTED` and inserts the transaction. This preserves snapshot consistency without composite FKs or triggers. If redundant participant/crop snapshot IDs are stored, verify they match the request/lot before insert.
- **Unresolved product/data decision:** whether gross/net amounts must equal formulas, rounding, and whether negative `net_amount` is allowed. The API can produce a negative request net and currently has no transaction net constraint; do not add `net_amount >= 0`.
- Indexes: unique indexes above; `(created_at DESC)` for admin recency; `(farmer_id,created_at DESC)` and `(buyer_id,created_at DESC)` for participant lists; `(transaction_status,payment_status)` only if filter workload merits it.
- Enums: payment `PENDING`, `PAYMENT_INITIATED`, `ESCROW_HELD`, `PAID`, `FAILED`, `REFUNDED`, `DISPUTED`; fulfillment `CONFIRMED`, `IN_TRANSIT`, `DELIVERED`, `COMPLETED`, `CANCELLED`.
- API transaction ID path parameter is internal integer `id`; public `transaction_id` is a receipt code. Complaint links use integer transaction row ID; notifications use the public code as reference text.

## 4. Atomicity, row locking, and state integrity

### Accepting a selling request and committing its lot

**Recommended implementation invariant:** implement a single database transaction for acceptance:

1. Lock the target `farmer_lots` row using `SELECT ... FOR UPDATE` (or use an equivalent conditional update with row count check).
2. Lock/re-read the selling request row and validate actor ownership/action authorization, that the request remains actionable, that the lot belongs to the requesting farmer, and that the lot is still `AVAILABLE`. The buyer accept endpoint checks buyer ownership; the farmer's generic action endpoint also accepts the full action enum, including `ACCEPT`, so the allowed actor/action matrix must be clarified before implementation.
3. Update the accepted request to `ACCEPTED` and lot to `COMMITTED` in that same transaction; update timestamps.
4. A committed lot must not be accepted again. Competing requests remain unchanged and cannot be accepted while the lot is committed.
5. Commit both row changes together. On any failure, roll back both. Return the existing conflict behavior when another accept has committed first.

**Verified by current code/tests:** the mock workflow changes the chosen request to `ACCEPTED` and its lot to `COMMITTED`; a second request against that committed lot gets a conflict. It does not update competing request statuses. **Unresolved product/data decision:** whether/how to later cancel, expire, or reopen competing requests.

Use a consistent lock order across all workflow paths (lot first, then request) to reduce deadlock risk. Add indexes supporting lookup by lot and request. Row locks do not replace uniqueness or authorization checks.

### Transaction creation and status changes

- **Verified by current code/tests:** route rejects requests not in `ACCEPTED`; one tested duplicate request returns 409; initial statuses are `CONFIRMED`/`PENDING`.
- **Recommended implementation invariant:** revalidate the accepted request and derive farmer, buyer, crop, quantity/unit, agreed price/unit, charges, and other relevant snapshot values from the linked request and lot inside one DB transaction. Keep `UNIQUE(transactions.selling_request_id)` and map concurrent uniqueness conflict to the existing 409 response. This consistency check can be done in repository logic; no complex composite FK or trigger is justified by current evidence.
- **Unresolved product/data decision:** receipt snapshot immutability/update policy.
- **Verified by current code/tests:** farmer can request `IN_TRANSIT` only and cannot set payment status; buyer can request `DELIVERED`/`COMPLETED` and payment `PAYMENT_INITIATED`/`ESCROW_HELD`; admin bypasses these role restrictions.
- **Unresolved product/data decision:** route documentation describes flows, but implementation does not validate prior-state transitions and tests do not define a full transition graph. Do not add transition constraints until specified.
- Notification persistence can be best effort as current `dispatch_in_app_notification` catches failures, or transactional/outbox-based for guaranteed delivery. Current behavior is best effort; do not claim atomic notification delivery.

### Status values versus transitions

- **Verified by current code/tests:** retain the enum values in Section 3. A value's presence in an enum does not establish its lifecycle transitions.
- **Verified by current code/tests:** request actions are accept, reject, counter, and cancel. The test mock maps them to `ACCEPTED`, `REJECTED`, `COUNTERED`, and `CANCELLED`; it treats `ACCEPTED`, `REJECTED`, `CANCELLED`, and `COMPLETED` as terminal, but does not mark `COUNTERED` or `EXPIRED` terminal. Tests cover accept, rejection, duplicate acceptance conflict, counter, and second request rejection because the lot is committed. This is test-double behavior, not a production repository implementation.
- **Verified by current code/tests:** buyer endpoints expose accept/reject; farmer endpoints expose the negotiation action. Buyer-offer `ACCEPTED` is guarded against withdrawal, but no current endpoint transitions an offer to accepted.
- **Verified by current code/tests:** creation initializes `CONFIRMED`/`PENDING`; role-specific target restrictions are stated above. The route does not verify a prior-state transition and the test double directly assigns status values.
- **Unresolved product/data decision:** full request, lot, transaction, and payment transition graphs; how `EXPIRED` is reached; reopening rejected/cancelled requests; setting lot `SOLD` and request `COMPLETED`; and payment failure/refund/dispute transitions. Do not add database transition constraints until defined.
- **Unresolved product/data decision:** farmer action route can submit `ACCEPT`, while a buyer-specific accept route also exists. Tests establish buyer acceptance but do not establish whether farmer acceptance is intended. Preserve route behavior until explicitly decided; enforce the approved actor/action matrix in workflow logic, not with a status enum constraint.

## 5. Units, monetary values, and price data

- Price discovery explicitly accepts `INR/kg` and `INR/quintal` and normalizes for comparison while retaining source units. Persist original market price in `price_unit`; do not silently rewrite source dataset values into a different unit.
- Lot, offer, request, and transaction each store both price and quantity unit, as the API requests/responses expose them. Preserve units in receipts. Unit compatibility and conversion factors must be centralized in application logic and tested; do not compare two prices unless normalized to the same unit.
- The proposal defaults crop standard unit to `kg`, while lot/offer/request API defaults are `quintal` and `INR/quintal`. This is a default mismatch, not an instruction to convert persisted values. Decide a canonical default for new records and how older records with absent unit fields are migrated.
- Proposed monetary values are INR by project context, but schemas encode currency in unit strings rather than a currency column. If multi-currency is in scope, add a currency code after product confirmation; do not infer it from locale formatting.
- `arrival_quantity` needs a separate `arrival_unit`; unlike the proposal, API schema explicitly includes it. Arrival may be unknown, so nullable is preferable to an invented zero; proposal default is zero. Choose whether unknown and measured zero must be distinguished.
- Keep API validation of positive trade quantities/prices and nonnegative costs. Decimal rounding should follow existing recommendation-service rules (two decimal places, half-up); persistence precision must avoid rounding before the intended calculation.

## 6. Deletion and retention policies

**Recommended implementation invariant:** safe deletion defaults:

- Use `ON DELETE RESTRICT`/`NO ACTION` for referenced users, profiles, crops, markets, lots, requests, and transactions. Avoid cascading deletion of trade or complaint history.
- User/profile deactivation should use `users.is_active` and buyer verification status, not hard delete, when audit/history exists.
- A farmer lot referenced by an offer/request should not be physically deleted; use `WITHDRAWN` while it is still eligible. Existing API's delete endpoint is a withdraw operation.
- Keep transaction, complaint, and notification records for the retention period approved by the project. If privacy policy requires erasure, define anonymization while retaining referentially valid audit records rather than cascade deletion.
- Crop/market deletion should be restricted when price history, lots, or predictions reference them; catalog retirement/soft-disable columns are not currently in API contracts and require approval before adding.
- Notification deletion/retention has no API delete endpoint; retention/cleanup policy is unresolved.

## 9. Unresolved product/data decisions

1. Define buyer eligibility for selling requests: whether the `users.id` must have role `BUYER`, have a related buyer profile, and meet a particular buyer-profile verification status. The `buyer_id` identifier itself is resolved as `users.id`.

4. Confirm market identity key, crop-name case/alias policy, and whether modal price must lie between min and max.
5. Decide what happens to competing requests after one commits the lot. Current behavior leaves them unchanged and rejects later acceptance while committed.
6. Partial sales: request/offer quantities may be below lot quantity; decide whether eventual partial sale/residual inventory is supported and how quantities/statuses change. Do not infer this from current validation.
7. Confirm whether negative net realization is acceptable for requests and transactions; current API can produce it. Confirm formula/rounding rules before adding amount checks.

11. Decide complaint respondent rules, whether complaint participants can be changed, and complaint/transaction retention.
12. Decide notification delivery reliability (current best-effort behavior versus transactional outbox) and retention.
13. Define the ML prediction input/output contract (including model/version, target date, confidence, units, freshness, retention) before implementing deferred `price_predictions`.
14. Choose enum versus checked text migration strategy and database support for future enum value changes.
